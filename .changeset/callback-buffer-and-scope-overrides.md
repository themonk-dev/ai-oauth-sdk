Four fixes: discovery endpoints on loopback, callbacks that own no flow, empty scope overrides, and `useAuth`'s client identity.

**A public `https` issuer may no longer name `http` loopback endpoints.** The endpoint check gave `http://127.0.0.1:<port>` the loopback pass unconditionally, while the redirect check next to it gives it only when the issuer was itself on loopback. The endpoint check now asks the same question. A local development server naming its own endpoints is ordinary; a public issuer naming one is the downgrade the redirect check already refuses — it points the authorization request, and the POST carrying the code, the PKCE verifier and the client secret, at whatever local process holds that port. A loopback issuer's document keeps working exactly as before, and an explicitly passed `authorizationUrl`/`tokenUrl` is still left alone.

**A callback for a flow the client never started no longer reaches the result buffer.** `completeAuthorization()` rejected on whatever `state` the request carried — on the `error=` branch with no lookup at all, and on the `code=` branch through the `catch` after `consume()` threw `unknown_state`. Buffered results are a fixed-size FIFO over every state at once, evicting the oldest at `maxSettled` (1000), so about a thousand unauthenticated requests to a public `/callback` — needing no code, no secret and no valid `state`, only the URL — pushed out every genuine buffered `TokenSet`. Those logins had already succeeded; their `waitFor()` then sat until it timed out. Both paths now write to the registry only for a `state` with a pending record this client owns, which is the same ownership rule `completeAuthorization()` already applies before exchanging a code. A denial or an exchange failure on a flow the client did start still reaches its waiters.

**`scopes: []` no longer drops the descriptor's scopes.** The spread in `resolveProvider()` had already copied the empty array over the base scopes, which left the `if (overrides.scopes?.length)` below it unable to do anything — dead code, and itself the evidence that an empty override was meant to be a no-op. `createAuthClient({ provider: 'claude', clientId, scopes: [] })` therefore emitted an authorize URL with no `scope` parameter at all, leaving the authorization server to pick whatever default it likes, with nothing in the URL to say the requested scopes had been dropped. An empty override is now the absence of one. A *base* descriptor that declares no scopes — OpenRouter — still emits none.

**`useAuth()` keys its client on the whole provider descriptor, not just its `id`.** `azureAi({ clientId, tenant })` hard-codes `id: 'azure-ai'` while scoping `authorizationUrl` and `tokenUrl` to the tenant, so two descriptors that differ only by tenant hashed equal: switching tenant returned the previous client, still pointed at the previous tenant's endpoints, and `getAccessToken()` went on serving that tenant's cached token. The docstring and the React guide both already said the store is rebuilt when something that changes the client's behaviour changes. Two limits are worth knowing: function-valued fields (`parseCallback`, `enrichTokens`, `apiHeaders`, `transformRequestBody`) do not survive `JSON.stringify`, so descriptors differing only in a hook still hash equal; and the key depends on property order, which is stable because `defineProvider` spreads a fixed literal. Re-keying separates the in-memory clients only — two of them for one `id` still read the same `tokens:<id>` record out of a persistent storage, which is what `accountKey` is for.
