Fence a refresh and a login that are already running when `logout()` is called, clear the credential a provider rename left behind, serialise `consume()` across every client sharing a store, re-read storage when a refresh is refused, and stop an abandoned login leaving its PKCE verifier at rest.

`logout()` cleared the token and returned while a refresh it knew nothing about was still on the wire. With a provider that rotates, that refresh came back holding a *new* refresh token and `setTokens()` wrote it: `isAuthenticated()` went from false back to true, and a live credential that nothing had revoked — `{ revoke: true }` correctly revoked the one the user actually held — sat in `auth.json` or `sessionStorage` under a user who had signed out. `AuthClient` now carries a logout epoch. `refresh()` captures it when it starts and refuses to write under a different one, so the rotated tokens are discarded and the call rejects with `aborted` rather than handing back a token the client has declined to keep; the in-flight promise is dropped at the same time, so a refresh started *after* the logout runs normally rather than joining a fenced one. Only writes are fenced, so a fresh login after a logout is untouched.

`AuthStore.logout()` had the same hole one level up, and no epoch could reach it: it never aborted the login controller the store already holds — unlike `cancel()` and `destroy()`, which both do. A login that landed after the sign-out took the UI from `{ isAuthenticated: false }` straight back to `{ isAuthenticated: true }`, with the tokens it had just stored. It now aborts first, so the login in flight fails as a cancellation and the code is never exchanged.

`logout()` deleted the token key for the current provider id only. `#readRenamedTokens()` migrates a credential stored under a *previous* id — `claude` before `anthropic`, `gemini` before `google`, `azure-ai` before `microsoft` — onto the current key on the next read, so the record was not forgotten, it was dormant: the first `getTokens()` after the sign-out restored the session, refresh token included. The CLI's plain `logout` hits this exactly, because it never reads first. Every `previousIds` key for the account is now deleted too — guarded, like the identical delete in `#readRenamedTokens()`, because an adapter that throws deleting a key would otherwise reject `logout()` *after* the live credential was already gone, and `AuthStore.logout()` skips `setState({ tokens: undefined })` on a rejection: the UI would show the user signed in after a sign-out that did clear their token.

`AuthorizationRegistry`'s per-state serialisation of `consume()` was held on the registry instance, and every `AuthClient` mints its own registry. Two clients over one storage object therefore both read the same pending record and posted the same code with the same verifier — two token-endpoint requests, and RFC 6749 §4.1.2 lets the authorization server revoke everything it has issued for a code it sees twice. That is the ordinary browser shape, not a contrived one: `createBrowserAuthClient` defaults to a `sessionStorage` adapter and the popup and redirect helpers build a client per call. The in-flight map now hangs off the storage object, so everyone handed the same adapter queues.

Which the browser default was not. `sessionStorageAdapter()`/`localStorageAdapter()` called `fromSyncStorage` on every call, and that returns a fresh object literal, so the two clients behind two `loginWithPopup()` calls keyed two different locks and serialised nothing — the lock was real and the default path walked around it. Both adapters now return one `AuthStorage` per backing `Storage` object, so the page's clients share one and the queue actually forms. Availability detection is unchanged and still runs per call: server-side rendering still gets the refusing adapter, a Web Worker still gets memory, and a store that throws on access still degrades to memory — which is deliberately *not* pooled, since sharing one `Map` across contexts the browser keeps apart is the thing that refusal exists to prevent.

The limits that remain are stated where they are enforced. The guarantee is the adapter object: two clients each wrapping the same backing store in an adapter of their own — `fromSyncStorage` called by hand, a `prefixedStorage` per client, a server minting a store per request — key different locks, and two processes over one `auth.json` share no memory at all. `AuthStorage` has no compare-and-swap, so closing those needs an atomic primitive on the interface.

`refresh()` re-read storage before the network call, to pick up a token another process had refreshed, but never after it. A window that lost the race then posted a refresh token the winner's rotation had already killed, and reported the session dead while the store it had just read held a perfectly usable token. The refusal path now reads once more and adopts a usable, different token before rethrowing.

`login()`'s `finally` only closed the receiver, so a timeout, an abort or a callback that failed the `state` check left `pending:<state>` — with the live `codeVerifier` in it — sitting in the credential file or `localStorage`. Nothing collected it, since `prune()` runs from `create()`: it stayed until the user happened to start another login. Those paths now delete the record through `cancelAuthorization()`. `completeAuthorization()` is deliberately outside that guard: it consumes the record on every path it can fail on, and rejecting the state twice would bury the real failure a later `waitForAuthorization()` should see.
