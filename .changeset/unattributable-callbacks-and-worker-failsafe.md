Stop an unattributable callback from failing a sign-in, keep the SSR failsafe on workerd, and bound OpenAI's device-flow timings.

**A page on another origin could cancel a live sign-in against a provider that echoes no `state`.** The documented redirect page runs `if (!postCallbackToOpener()) await announceCallback()`, and `window.opener` is `null` for anything that did not open it as a popup — a cross-origin `<a target="_blank" rel="noopener">` is enough, no iframe required. So an attacker gets this origin's own redirect page loaded with `?error=access_denied`, it falls through to `announceCallback()`, and the denial arrives on the same-origin `BroadcastChannel` every waiting `popupReceiver` listens to. Where the attempt has a `state` to compare, that payload was already dropped. Where it has none — OpenRouter strips `state` in `buildAuthParams`, so the authorization URL carries nothing to match on — the receiver took it and `login()` rejected with `authorization_denied`, off-origin and on demand. The client's own `state` comparison never runs on a receiver that threw.

A broadcast that reads as a *failure* now has to echo the presented `state` before it may settle the attempt; a success is accepted as before, so the `?code=` callback such a provider actually sends still completes the login. The same rule goes on the React Native deep-link receiver, where a custom URL scheme is open to every app on the device for the same reason.

The trade-off, the one the Node loopback receiver already took: a genuine denial from a provider with no `state` to match on no longer fails fast. Against OpenRouter — the one bundled provider in that shape — `login()` used to reject with `authorization_denied` the moment the user clicked deny, and now does not; the attempt ends on its deadline instead. In a popup that is usually sooner, because those providers leave `window.opener` intact and the close-poll still reports `aborted` once the user closes the popup the denial is sitting in. React Native's deep-link receiver has no such poll, so there it is the deadline or nothing.

Which is why `login()` now supplies a deadline for exactly these flows when the caller passed no `timeoutMs`: a provider declaring `echoesState: false`, or an authorization URL carrying no `state` at all. Without one, an OpenRouter login on React Native that the user denied never returned, and `pending:<state>` — the live PKCE verifier in it — sat in storage for the record's full life, which is the defect the sibling changeset closes. The bound is the pending record's own TTL, ten minutes by default: long enough for a real sign-in, and past it the record the exchange needs has expired anyway, so waiting longer cannot succeed. When it fires the login ends as `timeout` and the pending record is deleted with it. Providers that echo `state` are unchanged and still wait as long as the caller wants; a denial that echoes the presented `state` still fails immediately.

This stays a patch rather than a minor. What changes for a caller is the error a denied stateless login reports and when — `timeout` on the deadline rather than `authorization_denied` at once — not whether the call returns: the indefinite-wait shape it could otherwise have introduced is bounded here rather than shipped, so no caller has to add a `timeoutMs` it did not need before.

This is availability only. The code-injection variant reaches `completeAuthorization()` with the attacker's code and this client's PKCE verifier, which a correctly implemented authorization server rejects — for a provider that echoes no `state`, PKCE is the backstop and nothing the receiver can do replaces it.

**`localStorageAdapter()`/`sessionStorageAdapter()` handed Cloudflare's workerd an in-memory store instead of the server refusal.** The Web Worker exemption tested `'WorkerGlobalScope' in globalThis`, which is `true` on workerd — a server, one process answering every request — so the guard that exists to stop exactly this returned `memoryStorage()`, and a module-scoped `Map` pooled one request's tokens where the next request could read them. The check now looks for `WorkerNavigator`, which is `[Exposed=Worker]` and present in every real worker scope, and which workerd does not expose. Sign-in from a genuine Web Worker is unchanged; plain Node SSR was never affected.

**OpenAI's device flow took `interval` and `expires_at` unbounded.** Its RFC 8628 sibling clamps both; this path did not, so `{"interval": 0.001}` turned the poll into a flood of requests and an `expires_at` in 2099 turned it into a loop that never gave up. Both are now bounded the same way — interval to 1–60 seconds, expiry to at most 24 hours — with the existing defaults still covering a missing or unparseable field.
