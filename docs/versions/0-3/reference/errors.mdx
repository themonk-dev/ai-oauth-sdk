```ts
import { isOAuthError, OAuthError } from '@ai-oauth-sdk/core'

try {
  await client.login({ receiver })
} catch (error) {
  if (isOAuthError(error)) {
    console.error(error.code, error.message)
  }
}
```

Use `isOAuthError` rather than `instanceof`. It narrows by name and shape, so it survives two copies
of the package on disk, which happens more often than you would like in a monorepo.

## The codes

| Code | Meaning | Usual response |
| --- | --- | --- |
| `authorization_denied` | The provider returned `error=` on the callback. Usually the user clicked Deny. | Tell them, offer to retry |
| `unknown_state` | No pending authorization matches this `state`. | The link was reused or is forged. Start over |
| `state_expired` | The pending authorization passed its TTL. | Start over silently |
| `state_mismatch` | Callback `state` did not match what was issued. | Treat as hostile. Do not retry automatically |
| `token_request_failed` | The token endpoint returned a non-2xx status. | Check `status` and `providerError` |
| `invalid_token_response` | 2xx, but the body was unusable. | Usually a provider change. Report it |
| `refresh_failed` | No refresh token, or the provider rejected it. | Re-run the login flow |
| `aborted` | An `AbortSignal` fired or something called cancel. | Nothing. This is a user action |
| `timeout` | The flow exceeded `timeoutMs`. | Offer to retry |
| `device_flow_failed` | Device authorization ended without approval. | Check any `devicePrerequisite` |
| `unknown_provider` | No descriptor for that id. | A typo, or use `defineProvider` |
| `configuration_error` | Required configuration missing, usually `clientId`. | Read the message. It names the option |
| `unsupported_runtime` | This runtime cannot do that. A popup with no `window`, for instance. | Pick a different receiver |

## Fields

Every `OAuthError` carries these, though most are only populated when they apply. `code` is the one
to branch on; the rest are for diagnosis and for logging.

| Field | Type | Description |
| --- | --- | --- |
| `code` | `OAuthErrorCode` | One of the above. |
| `message` | `string` | Human-readable, with credentials already scrubbed. |
| `providerError` | `string` | Raw error field from the provider, when supplied. |
| `providerErrorDescription` | `string` | Raw error_description from the provider, when supplied. |
| `status` | `number` | HTTP status, for failures from a network response. |
| `state` | `string` | The state the failure relates to, when applicable. |
| `cause` | `unknown` | The underlying error, standard Error option. |

## Branching on a server

```ts
import { isOAuthError } from '@ai-oauth-sdk/core'

try {
  await client.completeAuthorization({ callbackUrl: req.url })
} catch (error) {
  if (!isOAuthError(error)) {
    throw error
  }

  switch (error.code) {
    case 'authorization_denied':
      return res.status(400).send('You declined the sign-in request.')
    case 'state_expired':
    case 'unknown_state':
      return res.redirect('/auth/login')
    case 'state_mismatch':
      // Someone sent a callback we did not issue. Log it, do not retry.
      logger.warn({ state: error.state }, 'state mismatch on callback')

      return res.status(400).send('Invalid sign-in request.')
    default:
      throw error
  }
}
```

`state_expired` and `unknown_state` are both ordinary. A user who left the tab open over lunch hits
the first; a user who reloaded the callback page hits the second, because the pending record is
consumed on the way through. Neither is worth an error page.

`state_mismatch` is different. It means a callback arrived carrying a `state` this client never
issued, which is what a CSRF attempt looks like. Do not paper over it with a retry.

## Credentials are scrubbed

Error messages pass through a redactor before they are constructed, so a token or a code that
appeared in a provider response does not end up in your logs.

```ts
import { redactSecrets, REDACTED, safeSnippet } from '@ai-oauth-sdk/core'

logger.error(redactSecrets(someProviderBody))
```

Those helpers are exported so you can apply the same treatment to anything you log yourself.
`safeSnippet` truncates as well, for when you want a hint of a response body without the body.

## Errors reach waiters

A failure in `completeAuthorization` is delivered to anyone blocked in `waitForAuthorization` for
the same `state`, not just to the caller. That is why `handleRedirectCallback` hands the whole URL
to `completeAuthorization` rather than checking for an error itself: a locally thrown error would
leave the waiters hanging until their timeout.
