The library obtains OAuth tokens and hands them to you. Once a token is in your process, protecting
it is your responsibility. Nothing here encrypts tokens in memory, and nothing here can stop your
application from logging or transmitting them.

What follows is what it does do.

## Reporting a vulnerability

Report privately rather than in a public issue, through
[GitHub's private vulnerability reporting](https://github.com/themonk-dev/ai-oauth-sdk/security/advisories/new)
for the repository. Include the affected version and package, a description, and ideally a
reproduction.

## Enforced

**PKCE is on by default**, with `S256`, for every redirect-based provider. The verifier is persisted
only for the flow's lifetime, ten minutes by default, and consumed exactly once, so a replayed
callback cannot replay the exchange.

**Randomness never degrades.** With no `crypto.getRandomValues` available the library throws rather
than falling back to `Math.random()`. A guessable `state` or PKCE verifier defeats the point of
both. SHA-256 does have a pure JavaScript fallback, because a hash handles no secrets, and that is
what makes PKCE work on Hermes with no native polyfill.

**`state` is verified on every callback, in constant time.** A plain `!==` short-circuits at the
first differing character, which in principle turns a 256-bit guess into an incremental one. The
practical risk is low, since an attacker also needs a usable `code` and the pending record is single
use, but the comparison sits on a security boundary.

**A callback carrying no `state` is rejected.** Anyone can reach a loopback port or post a message
to an opener, so omitting the parameter must not become a way to skip the check. If you write your
own receiver, it has to return the `state` it received.

**The loopback server binds `127.0.0.1`**, never `0.0.0.0`, answers `GET` and `HEAD` only, and
serves exactly one callback before shutting down. It sends `no-store`, `no-referrer` and `nosniff`
on every response, because the callback URL carries the authorization code in its query string and
must not be cached or leak through a `Referer`.

**Popup callbacks are origin-checked** before being trusted, and `postCallbackToOpener` posts to its
own origin rather than to `*`.

**`announceCallback` broadcasts on your own origin, to everything listening on it.** A
`BroadcastChannel` cannot be opened from another origin, so the code does not leave yours — but it
does not reach one window the way `postMessage` does. Every same-origin context is in the audience,
your other tabs and your own iframes included. `popupReceiver` compares `state` and ignores a
callback minted for a different attempt, and the client compares it again before exchanging, so a
callback taken by the wrong tab fails rather than completing. Use it on redirect pages that need it
— an authorization page that severs `window.opener` leaves no alternative — and prefer
`postCallbackToOpener` wherever the opener survived.

**`logout()` beats a refresh already on the wire.** Clearing the local record is synchronous, but a
token request dispatched a moment earlier cannot be recalled, and a provider that rotates answers it
with a new access *and* refresh token a round trip later. Written back, that would restore the
session in memory and on disk. A refresh that returns after a `logout()` therefore writes nothing
and rejects with `aborted`, and a call arriving after the sign-out starts fresh rather than joining
it. `logout()` itself still never waits for the network.

**A provider id a built-in has shed is a name, not an identity.** `claude` was `anthropic`, `gemini`
was `google`, `azureAi` was `microsoft`, and each still adopts a credential stored under its old id
and completes a flow started under one. Since anything can claim a name a provider let go of, such a
record now has to agree on the token endpoint too. Records naming no endpoint — everything written
before the field existed, which is the version a rename migrates from — are still accepted, so
upgrading signs nobody out. `reservedProviderIds` exports every id the built-ins answer to, current
and shed; the CLI refuses all of them for `--authorize-url`/`--token-url`.

**Errors never carry a credential.** A failed token request quotes a snippet of the provider's
response, which is genuinely useful for diagnosis. But that body is not ours, and a misconfigured
gateway echoing the request back would put a live refresh token straight into your logs. Snippets
pass through `redactSecrets()` first.

<Callout type="warn" title="Redaction is defence in depth, not a guarantee">
  It scrubs the OAuth credential parameters and the token shapes the supported providers issue. Do
  not rely on it to make an arbitrary secret safe to print.
</Callout>

OpenAI's device flow gets one extra step, because its `device_auth_id` and `user_code` are not
identifiers: posted back as a pair they return an authorization code *and* the PKCE verifier that
redeems it, so between them they are the whole approval credential. Name-based redaction is not
enough for a value a provider mentions in prose rather than as a parameter, so a failed poll scrubs
those two values out of the snippet by value before quoting it. That works only because they are
this process's own codes — it does nothing for a credential the library never held.

## Left to you

**Storage.** Pluggable, and defaults to memory.

| Adapter | Protection |
| --- | --- |
| `fileStorage()`, Node | `0600`, atomic temp-file rename |
| `sessionStorageAdapter()`, browser default | Survives the redirect, not the tab |
| `localStorageAdapter()`, browser | Readable by any script on the origin |
| `secureStoreAdapter()`, Expo | Keychain, EncryptedSharedPreferences |
| `asyncStorageAdapter()`, React Native | **Not encrypted at rest** |

`fileStorage()` reads an empty `dir`, or an empty `AI_OAUTH_SDK_HOME`, as unset and falls back to
`~/.ai-oauth-sdk` rather than treating it as a directory: joining an empty directory with the file
name yields the relative path `auth.json`, which would put the credential file wherever the process
happened to start — in CI, the checked-out repository. The file would still be `0600`, so that was
a credential written somewhere nobody chose rather than one exposed to other local users; the cost
is
that it outlives the job in a git tree or a build artifact, and that the path the CLI reported back
does not exist to go and delete.

Prefer `secureStoreAdapter` for refresh tokens on mobile. In a browser, remember that any XSS on
your origin can read whatever web storage you chose.

The web storage adapters fall back to memory where the browser throws on access, and in a browser
Web Worker, but refuse off a browser entirely — see [Storage](/docs/reference/storage). Cloudflare
Workers and other workerd-based runtimes count as
servers here, not as browsers. Their global exposes `WorkerGlobalScope`, but one isolate serves many
users' requests, so an in-memory store there is a single `Map` holding every one of their tokens.
`localStorageAdapter()` and `sessionStorageAdapter()` refuse on any runtime they cannot positively
identify as a browser Web Worker; supply `storage:` explicitly if you are on one they do not
recognise.

**`TokenSet.raw`** holds a second copy of every credential, because it is the token endpoint's
response verbatim. Do not log it or ship it to telemetry.

**A shared machine.** Any local process can in principle connect to a loopback port. That is
inherent to RFC 8252, and it is why PKCE matters: without the verifier, a code observed on that
port is not enough.

**JWTs are decoded, never signature-verified.** They arrive over TLS directly from the token
endpoint and are read only for convenience fields. Do not pass a third-party token to
`decodeJwtPayload` and treat the result as authenticated.

## The multi-user caveat

<Callout type="error" title="OpenRouter has no CSRF guard">
  Providers that do not return `state` set `echoesState: false`, and the library resolves the
  callback against the most recently started flow instead. That is fine for a CLI or a single-flow
  app. In a multi-user server it means one user's callback can complete another user's login. See
  [OpenRouter](/docs/providers/openrouter).
</Callout>

## Client credentials

The ids shipped for ChatGPT, Claude, GitHub Copilot, Qwen, Gemini and Grok are public,
PKCE-protected values published by those vendors' own CLIs. They are not secrets.

One client secret is embedded, Gemini's, because its token endpoint refuses an installed-app
exchange without one and those secrets are documented as non-confidential. Everything is
overridable. See [credentials](/docs/resources/credentials).

The CLI never persists a client secret. It reads one from `--client-secret` or
`AI_OAUTH_SDK_CLIENT_SECRET` per invocation, so a value that was transiently visible in `ps` does
not become a durable copy on disk. Prefer the environment variable, since a flag lands in shell
history too.

## Supply chain

Published tarballs carry npm provenance. Every package is published from CI with
`provenance: true`, producing a signed attestation that links the tarball to the commit and
workflow that built it:

```bash
npm audit signatures
```

The release pipeline is split deliberately. The half that installs dependencies and runs the build
holds no credentials of any kind and no cache, and hands over a directory of tarballs. The half
that can mint an npm credential installs nothing and runs no project code. Trusted publishing does
not remove the credential, it makes it mintable on demand, so any code running in a job that holds
`id-token: write` can mint one.

## Supported versions

Before 1.0, fixes land on the latest minor. Once 1.0 ships, the current major receives security
fixes.

Runtime support tracks Node's own calendar. The packages declare `engines: >=22` and CI covers Node
22, 24 and 26. Node 18 and 20 are past end of life and are no longer tested. The code depends on
nothing newer, so they will very likely still work, but do not rely on it for anything you care
about.
