## Getting started

Node 24 is pinned in `.nvmrc`, so `nvm use` picks it up. CI also runs 22 and 26.

```bash
pnpm install
pnpm verify   # lint, typecheck, build, test, exports check
```

Run `pnpm verify` before opening a pull request. `pnpm test` alone is not enough: vitest transpiles
with esbuild and never typechecks, so a suite can be green while the package does not compile.

```bash
pnpm test:watch                # while iterating
pnpm vitest run packages/core  # one package
pnpm vitest run -t "refresh"   # one test by name
```

## Layout

```
packages/
  core/         zero-dependency engine: PKCE, registry, exchange, refresh, providers, store
  node/         loopback server, file storage, browser launcher
  browser/      popup and redirect receivers, web storage
  cli/          the ai-oauth-sdk binary
  react/ vue/ svelte/ solid/    UI bindings, all thin wrappers over the core store
  react-native/ deep link and auth session, SecureStore
  ai-oauth-sdk/ umbrella package and the CDN bundle
docs/           this site
```

<Callout type="warn" title="Core stays dependency-free and platform-free">
  No `node:` imports, no DOM globals at module scope, no npm dependencies. Anything
  platform-specific belongs in an adapter package. That constraint is what lets the same code run in
  a CLI, a browser, Hermes and a script tag.
</Callout>

## Adding a provider

Most providers need only a descriptor in `packages/core/src/providers/`. Start from an existing one
that shares the same shape, and read [custom providers](/providers/custom) for what every field
does.

If the provider leaves the spec, use the hooks rather than adding a branch to the flow code.
`buildAuthParams`, `parseTokenResponse` and `parseCallback` were added for exactly that, and
OpenRouter is the proof that they are enough.

Include in the pull request where the values came from. An endpoint or client id observed in a
vendor's shipped CLI should say which tool and which version.

## Tests

The flow tests drive a real OAuth server that validates PKCE by recomputing the S256 challenge, so a
broken verifier fails the suite rather than only failing in production. Add to that rather than
mocking, and see [testing your integration](/recipes/testing) for how to use the same approach in
your own project.

## Commits and releases

Changesets. Add one with `pnpm changeset` describing what changed from a consumer's point of view.
All ten packages are held at the same version, so a patch to the core bumps everything.

## Working on these docs

The site is a React Router app under `docs/`, deliberately outside the pnpm workspace so its
dependencies stay out of the root lockfile and out of the audit gate that covers the published
packages.

```bash
cd docs
pnpm install
pnpm dev      # http://localhost:5173
pnpm build    # static output in build/client
```

Content is MDX under `docs/content`, and the sidebar is driven by the `meta.json` files next to it.
`Tabs`, `Steps`, `Accordions`, `TypeTable`, `Callout` and `Cards` are registered globally, so pages
do not need to import them.

## Reporting security issues

Privately, through
[GitHub's private vulnerability reporting](https://github.com/themonk-dev/ai-oauth-sdk/security/advisories/new).
Not in a public issue.
