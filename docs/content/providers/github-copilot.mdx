```ts
import { createNodeAuthClient, publicClientIds } from '@ai-oauth-sdk/node'

const client = createNodeAuthClient({
  provider: 'github-copilot',
  clientId: publicClientIds['github-copilot'],
})

const tokens = await client.deviceLogin({
  onCode: ({ verificationUri, userCode }) =>
    console.log(`Open ${verificationUri} and enter ${userCode}`),
})
```

| Setting | Value |
| --- | --- |
| Authorization | `https://github.com/login/oauth/authorize` |
| Token | `https://github.com/login/oauth/access_token` |
| Device | `https://github.com/login/device/code` |
| Scopes | `read:user`, `copilot` |
| PKCE | no |
| API base | named by the token exchange, `https://api.githubcopilot.com` as a fallback |

## Device flow only

GitHub's OAuth app for Copilot has no registered redirect URI, so the authorization-code flow is
unavailable. `client.login()` has nothing to redirect to. Use `deviceLogin()`.

GitHub's device flow does not use PKCE, which is why the descriptor sets `usePkce: false`. That is
GitHub's design rather than an omission here: the device grant has no redirect to intercept, and
the device code is delivered over a back channel.

## The token you get is not a Copilot token

The `ghu_` token GitHub returns is a GitHub token, and Copilot's API does not accept it. It wants a
short-lived Copilot token obtained by exchanging that one, and the exchange response also names the
host to send it to. So neither the credential nor the base URL is knowable from the descriptor.

`createAuthenticatedFetch` does the whole thing:

```ts
import { createAuthenticatedFetch } from '@ai-oauth-sdk/core'

const api = createAuthenticatedFetch(client)

// Exchanged token, correct host, editor headers, all of it.
const response = await api('/chat/completions', {
  method: 'POST',
  body: JSON.stringify({ model: 'gpt-4o', messages: [{ role: 'user', content: 'hi' }] }),
})
```

It caches the exchanged token until shortly before it expires, and re-runs the exchange on a 401
rather than refreshing the GitHub token, since the short-lived token is the part that goes stale.

<Callout type="warn" title="Name your editor">
  Copilot refuses a request that does not say which editor it came from, so the descriptor sends
  `Copilot-Integration-Id` and `Editor-Version` with the values an editor client uses. Pass
  `headers: { 'Editor-Version': 'my-cli/1.0' }` to `createAuthenticatedFetch` to identify as
  yourself instead.
</Callout>

## The API host is data

Individual accounts get `api.individual.githubcopilot.com`; enterprise accounts get a host of their
own. Hard-coding `api.githubcopilot.com` works for some users and not others, which is why the
descriptor treats it as a fallback and the exchange result wins.

## Driving it by hand

`exchangeForCopilotToken` is still exported for anyone not using the fetch:

```ts
import { exchangeForCopilotToken } from '@ai-oauth-sdk/core'

const copilot = await exchangeForCopilotToken(tokens)

copilot.token // short-lived Copilot API token
copilot.expiresAt // about 30 minutes out
copilot.apiBaseUrl // the host for this account, when GitHub names one
copilot.raw // endpoints and feature flags GitHub returns alongside
```

Fetch that per session rather than storing it. The durable credential is the GitHub token in your
`TokenSet`. A 25 to 30 minute session token is short enough that any long-running process will
cross it, so do not capture it in a closure.

## Two client ids exist

VS Code's Copilot extension and the Copilot CLI publish different ids. `publicClientIds['github-copilot']`
is the VS Code one. Both work for the device flow; they differ in what GitHub attributes the usage
to.

## Registering your own

**GitHub > Settings > Developer settings > OAuth Apps**. Enable the device flow on the app, and
request the `copilot` scope. Whether a self-registered app can reach the Copilot API depends on the account's entitlement
rather than on the OAuth app, so test it before shipping.
