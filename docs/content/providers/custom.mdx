The built-ins are a convenience. The flow code has no idea which provider it is running, so
anything that speaks OAuth 2.0 works.

## defineProvider

```ts
import { createAuthClient, defineProvider } from '@ai-oauth-sdk/core'

const acme = defineProvider({
  id: 'acme',
  label: 'Acme AI',
  clientId: 'my-client-id',
  authorizationUrl: 'https://auth.acme.dev/authorize',
  tokenUrl: 'https://auth.acme.dev/token',
  scopes: ['openid', 'inference'],
  redirect: { mode: 'loopback', loopbackPort: 0 },
})

const client = createAuthClient({ provider: acme })
```

`defineProvider` fills in what almost every provider shares: PKCE on, `S256`, a form-encoded token
request with the client id in the body, `/callback` as the loopback path, and `localhost` as the
loopback host. State only what makes yours different.

## From an OIDC discovery document

```ts
import { providerFromDiscovery } from '@ai-oauth-sdk/core'

const acme = await providerFromDiscovery('https://auth.acme.dev', {
  id: 'acme',
  label: 'Acme AI',
  clientId: 'my-client-id',
  redirect: { mode: 'loopback', loopbackPort: 0 },
})
```

Pass the issuer URL, not the `.well-known` path. It fetches
`/.well-known/openid-configuration` and takes `authorization_endpoint`, `token_endpoint`,
`device_authorization_endpoint` and `scopes_supported` from it.

This is the more durable option for anything long-lived, because an endpoint move needs no release
on your side. Anything you pass explicitly still wins over the document.

## The escape hatches

Three fields exist for providers that leave the spec. Between them they are enough to keep even
OpenRouter working without a special case in the flow code.

A provider that names its redirect parameter something else and returns its token under a different
key:

```ts
const odd = defineProvider({
  id: 'odd',
  label: 'Odd',
  authorizationUrl: 'https://odd.example/auth',
  tokenUrl: 'https://odd.example/keys',
  scopes: [],
  redirect: { mode: 'loopback', loopbackPort: 0 },
  requiresClientId: false,
  echoesState: false,
  tokenRequest: { style: 'json', includeClientIdInBody: false },
  buildAuthParams: (params) => ({ callback_url: params.redirect_uri ?? '' }),
  parseTokenResponse: (raw) =>
    typeof raw.key === 'string' ? { ...raw, access_token: raw.key, token_type: 'Bearer' } : raw,
})
```

That is, more or less, the OpenRouter descriptor.

## Enrichment and API headers

Two more hooks, both optional and both about what happens after the token arrives.

```ts
defineProvider({
  // ...
  enrichTokens(raw, tokens) {
    const payload = decodeJwtPayload(tokens.idToken)

    return { accountId: getStringClaim(payload, 'sub'), email: getStringClaim(payload, 'email') }
  },
  apiHeaders: (tokens) => ({ 'x-account-id': tokens.accountId ?? '' }),
})
```

`enrichTokens` derives `accountId` and `email` so `whoami` has something to print.
`apiHeaders` is what `createAuthenticatedFetch` attaches to every request, which is how Anthropic's
beta flag and OpenAI's account header get sent without you doing anything.

## From the CLI

```bash
ai-oauth-sdk login acme --client-id my-client \
  --authorize-url https://auth.acme.dev/authorize \
  --token-url https://auth.acme.dev/token \
  --device-url https://auth.acme.dev/device
```

Same descriptor, built from flags. Useful for trying a provider before writing any code.
