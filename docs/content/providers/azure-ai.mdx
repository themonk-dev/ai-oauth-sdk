```ts
import { azureAi, createAuthClient } from '@ai-oauth-sdk/core'

const provider = azureAi({
  clientId: 'your-app-registration-id',
  tenant: 'contoso.onmicrosoft.com',
})

const client = createAuthClient({ provider })
```

Entra ID is the login. The token it mints is for the Azure AI Services resource, which is what both
Azure AI Foundry and the Azure OpenAI data plane accept, since a Foundry resource is an AI Services
resource underneath. One scope covers both.

Every other built-in is a constant. This one is a function, because the endpoints contain the tenant
and there is no public client id to ship. Every Azure app registration is its own client.

<Callout type="warn" title="Renamed in 0.4">
  This was `microsoft` before 0.4, both as the exported `microsoft()` factory and as the provider
  id. Both are now `azureAi` and `azure-ai`. A credential stored under the old id is found and moved
  the first time you sign in, so nobody is signed out by the rename. The
  [0.3 docs](/docs/v/0-3/providers/microsoft) cover the old names.
</Callout>

## Options

| Option | Type | Description |
| --- | --- | --- |
| `clientId` | `string` | **Required.** Your registered application (client) id. |
| `tenant` | `string` | A tenant GUID, a domain, or one of the multi-tenant aliases (common, organizations, consumers). Defaults to `common`. |
| `scopes` | `string[]` | Replaces the default scope set. Defaults to `Azure OpenAI's .default scope plus offline_access, openid, profile`. |
| `loopbackPort` | `number` | Loopback port. 0 picks a free one, which Entra accepts. Defaults to `0`. |

## What it builds

For tenant `T`, the endpoints are all under
`https://login.microsoftonline.com/T/oauth2/v2.0`:

| Setting | Value |
| --- | --- |
| Authorization | `/authorize` |
| Token | `/token` |
| Device | `/devicecode` |
| Logout | `/logout` |
| Userinfo | `https://graph.microsoft.com/oidc/userinfo` |

Default scopes are `https://cognitiveservices.azure.com/.default`, `offline_access`, `openid` and
`profile`. The first is the Azure AI Services resource, which is what grants access to the models;
the `.default` suffix tells Entra to issue whatever the app registration has been consented for,
rather than asking per-scope.

## Registering the app

In **Entra ID > App registrations > New registration**. Then:

1. Under **Authentication > Add a platform > Mobile and desktop applications**, add a redirect URI of
   `http://localhost`. Entra ignores the port for loopback URIs, which is why `loopbackPort: 0`
   works.
2. Under **Authentication > Advanced settings**, set **Allow public client flows** to yes. That is what lets PKCE work without a client secret.
3. Under **API permissions > Add a permission**, add the Azure AI Services delegated permission
   your app needs, then grant consent. It may be listed under its older name, Cognitive Services.

Do not add a client secret. A public client with PKCE is the correct shape for a desktop or CLI
application, and a secret shipped in one is not a secret.

## Device flow

Entra's device grant is ordinary RFC 8628, so it works with no extra configuration:

```ts
const tokens = await client.deviceLogin({
  onCode: ({ verificationUri, userCode }) =>
    console.log(`Open ${verificationUri} and enter ${userCode}`),
})
```

Note that conditional access policies can block the device flow at the tenant level, in which case
the approval page refuses rather than the endpoint. That looks like a login that never completes.

## Multi-tenant

`tenant: 'common'` accepts both work and personal accounts. `organizations` restricts to
work accounts, `consumers` to personal ones. A specific GUID or domain restricts to that directory,
which is usually what you want for an internal tool.

## Calling the API

The base URL is your own resource, so set it yourself rather than relying on the descriptor. There
is no `apiBaseUrl` on this descriptor for that reason:

```ts
const api = createAuthenticatedFetch(client, {
  baseUrl: 'https://my-resource.openai.azure.com/openai',
})

const response = await api('/deployments/gpt-5/chat/completions?api-version=2024-10-21', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ messages: [{ role: 'user', content: 'hi' }] }),
})
```

The bearer token is accepted in place of the `api-key` header when the resource is configured for
Entra authentication.

The path above is the classic Azure OpenAI shape. A resource provisioned through Foundry may serve
a different one, so take the endpoint from your resource in the portal rather than assuming.
