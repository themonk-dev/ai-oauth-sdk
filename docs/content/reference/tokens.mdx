`TokenSet` is data, not behaviour. It is what `login()`, `deviceLogin()` and
`completeAuthorization()` resolve with, and what `getTokens()` reads back out of storage. The
methods that produce and renew it live on [AuthClient](/docs/reference/auth-client).

```ts
interface TokenSet {
  accessToken: string
  refreshToken?: string
  expiresAt?: number
  tokenType: string
  scope?: string
  idToken?: string
  accountId?: string
  email?: string
  provider: string
  tokenEndpointOrigin?: string
  raw: Record<string, unknown>
}
```

| Field | Type | Description |
| --- | --- | --- |
| `accessToken` | `string` | The bearer credential. |
| `refreshToken` | `string` | Absent when the provider does not issue one, as with OpenRouter. |
| `expiresAt` | `number` | Absolute expiry in epoch milliseconds. Absent when the provider omits one. |
| `tokenType` | `string` | Usually Bearer. |
| `scope` | `string` | What was actually granted, which may be less than asked. |
| `idToken` | `string` | OIDC id token, where one was returned. |
| `accountId` | `string` | Provider account identifier, when derivable. |
| `email` | `string` | Account email, when the provider returns or encodes one. |
| `provider` | `string` | The provider id this token belongs to. |
| `tokenEndpointOrigin` | `string` | Origin of the token endpoint that issued it. Recorded by `setTokens()`; absent on records written before this field existed. |
| `raw` | `Record<string, unknown>` | The untouched token-endpoint response. |

<Callout type="error" title="raw holds a second copy of every credential">
  It is the response verbatim, so it contains `access_token`, `refresh_token` and `id_token` again.
  Do not log it, serialise it into telemetry, or return it from an API. The named fields are what
  you want. Reach into `raw` only for something a provider returns that this interface has no name
  for.
</Callout>

## Where it came from

`tokenEndpointOrigin` records the origin of the endpoint that issued the token set. You do not write
it — `setTokens()` stamps it — and you rarely read it. It exists so a provider that has been renamed
can tell a credential it minted under its old id from one that merely sits under a name it used to
have, which is a name anything can claim; see [Security](/docs/resources/security). A record written
by an older version carries no origin and is taken as the rename it is.

## Expiry

`expiresAt` is absolute, not a duration. The library converts `expires_in` at the moment the
response arrives, which avoids the class of bug where a duration is stored and later compared
against the wrong clock reading.

A token is treated as expired `expirySkewMs` before its real expiry, 60 seconds by default. That
window exists so a request that starts just under the wire does not arrive just over it.

```ts
import { isExpired, DEFAULT_EXPIRY_SKEW_MS } from '@ai-oauth-sdk/core'

isExpired(tokens) // uses the default skew
isExpired(tokens, 0) // strict
```

A token with no `expiresAt` is never considered expired, which is correct for OpenRouter's durable
key and wrong for nothing else currently.

## Getting a fresh one

```ts
await client.getAccessToken() // refreshes if inside the window
await client.refresh() // refreshes regardless
```

Both are documented on [AuthClient](/docs/reference/auth-client#tokens), including how concurrent
callers share a single refresh and how a token rotated by another process is picked up. Nothing
about that behaviour is on the token set itself.

## Several accounts

```ts
const work = createAuthClient({ provider: ProviderId.Claude, clientId, accountKey: 'work' })
const personal = createAuthClient({ provider: ProviderId.Claude, clientId, accountKey: 'personal' })
```

`accountKey` changes the storage key from `tokens:claude` to `tokens:claude:work`. Nothing
else about the client changes. On the CLI that is `--account`.

## Reading the identity

`accountId` and `email` are derived by the provider's `enrichTokens` hook, usually out of the
`id_token`. They cost nothing, because the claim is already in hand.

For providers with an OIDC userinfo endpoint there is also a network call:

```ts
import { fetchUserInfo } from '@ai-oauth-sdk/core'

const user = await fetchUserInfo(client)
user.sub
user.email
user.name
```

It throws `configuration_error` when the provider declares no userinfo endpoint. Prefer the fields
on the token set when they are populated.

## Ending a session

Three built-ins declare a `revocationUrl`, and only two of them are RFC 7009 revocation endpoints:
`gemini` and `xai`. `azure-ai` points at Entra's end-session endpoint, which ends the sign-in session
rather than revoking the token itself — `revoke()` will call it, but do not read a successful call as
the token having been withdrawn. For every other provider, clearing the local copy is all anyone can
do from here.
[`revoke()` and `logout()`](/docs/reference/auth-client#session) are the methods.

## Inspecting a JWT

```ts
import { decodeJwtPayload, getClaim, getStringClaim } from '@ai-oauth-sdk/core'

const payload = decodeJwtPayload(tokens.idToken)
const email = getStringClaim(payload, 'email')
```

This decodes. It does not verify a signature, and it is not a substitute for verification if you
are making a trust decision on the contents.
