  expiresAt?: number

<Callout type="error" title="raw holds a second copy of every credential">
  It is the response verbatim, so it contains `access_token`, `refresh_token` and `id_token` again.
  Do not log it, serialise it into telemetry, or return it from an API. The named fields are what
  you want. Reach into `raw` only for something a provider returns that this interface has no name
  for.
</Callout>

## Expiry

`expiresAt` is absolute, not a duration. The library converts `expires_in` at the moment the
response arrives, which avoids the class of bug where a duration is stored and later compared
against the wrong clock reading.

A token is treated as expired `expirySkewMs` before its real expiry, 60 seconds by default. That
window exists so a request that starts just under the wire does not arrive just over it.

```ts
import { isExpired, DEFAULT_EXPIRY_SKEW_MS } from '@ai-oauth-sdk/core'

isExpired(tokens) // uses the default skew
isExpired(tokens, 0) // strict
```

A token with no `expiresAt` is never considered expired, which is correct for OpenRouter's durable
key and wrong for nothing else currently.

## Refresh

```ts
await client.getAccessToken() // refreshes if inside the window
await client.refresh() // refreshes regardless
```

Two things make this safe under concurrency.

**In-process.** A refresh in flight is shared. Ten callers waking to an expired token get one
network request between them, which matters because providers that rotate refresh tokens would have
had nine of those requests invalidate each other.

**Cross-process.** Before refreshing, storage is re-read. If another process already refreshed and
the stored token is usable, it is taken instead. Two CLI windows open at once is an ordinary
situation, and no promise can coordinate across processes.

## Several accounts

```ts
const work = createAuthClient({ provider: 'anthropic', clientId, accountKey: 'work' })
const personal = createAuthClient({ provider: 'anthropic', clientId, accountKey: 'personal' })
```

`accountKey` changes the storage key from `tokens:anthropic` to `tokens:anthropic:work`. Nothing
else about the client changes. On the CLI that is `--account`.

## Reading the identity

`accountId` and `email` are derived by the provider's `enrichTokens` hook, usually out of the
`id_token`. They cost nothing, because the claim is already in hand.

For providers with an OIDC userinfo endpoint there is also a network call:

```ts
import { fetchUserInfo } from '@ai-oauth-sdk/core'

const user = await fetchUserInfo(client)
user.sub
user.email
user.name
```

It throws `configuration_error` when the provider declares no userinfo endpoint. Prefer the fields
on the token set when they are populated.

## Revocation

```ts
await client.revoke() // refresh token by default
await client.revoke({ tokenType: 'access_token' })
await client.logout({ revoke: true }) // revoke, then clear locally
```

Only `google`, `xai` and `microsoft` declare a revocation endpoint among the built-ins. For the
others, `logout()` clears the local copy and that is all anyone can do from here.

## Inspecting a JWT

```ts
import { decodeJwtPayload, getClaim, getStringClaim } from '@ai-oauth-sdk/core'

const payload = decodeJwtPayload(tokens.idToken)
const email = getStringClaim(payload, 'email')
```

This decodes. It does not verify a signature, and it is not a substitute for verification if you
are making a trust decision on the contents.
