```ts
interface CallbackReceiver {
  readonly id: string
  start(context: ReceiverContext): Promise<StartedReceiver>
}

interface StartedReceiver {
  redirectUri: string
  present(url: string): Promise<void>
  wait(): Promise<CallbackResult>
  close(): Promise<void>
}
```

`redirectUri` has to be final by the time `start()` resolves, because it goes into the
authorization request. `close()` has to be safe to call whether or not `wait()` ever settled.

## From @ai-oauth-sdk/core

The core ships one receiver, because it is the only kind that needs nothing from the platform. A
prompt is whatever function you give it.

### manualReceiver(options)

Prints or displays the URL through a callback you supply, then reads back whatever the user gives
you.

```ts
manualReceiver({
  redirectUri: 'https://example.com/callback',
  prompt: async (url) => showModalAndAwaitPaste(url),
})
```

The returned string is parsed with the provider's own parser, so a full URL, a bare code, or
Claude's `code#state` all work.

## From @ai-oauth-sdk/node

Three receivers, covering the desktop case, the headless case, and the case where you cannot tell
which you are in. `defaultReceiver()` picks between the first two for you — `hybridReceiver` is
opt-in, since choosing it is a decision about your own environment that a heuristic should not make
on your behalf.

### loopbackReceiver(options)

A one-shot HTTP server on `127.0.0.1`.

| Option | Type | Description |
| --- | --- | --- |
| `port` | `number` | 0 picks a free one. Defaults to `the provider's port`. |
| `path` | `string` | Defaults to `the provider's path`. |
| `host` | `string` | Defaults to `127.0.0.1`. |
| `redirectHost` | `string` | Host used in the redirect URI, if it differs. |
| `openBrowser` | `boolean` | Defaults to `true`. |
| `onAuthorizationUrl` | `(url: string) => void` |  |
| `successHtml` | `string` |  |
| `failureHtml` | `(error: string) => string` |  |

Answers `GET` and `HEAD` only, on the configured path only, exactly once.

### promptReceiver(options)

Prints the URL and reads the pasted result from stdin.

| Option | Type | Description |
| --- | --- | --- |
| `redirectUri` | `string` | Defaults to `the provider's hosted callback`. |
| `openBrowser` | `boolean` | Defaults to `true`. |
| `message` | `(url: string) => string` |  |
| `signal` | `AbortSignal` | Abandons the pending read. |

### hybridReceiver(options)

Both of the above at once, first one wins. Takes everything `loopbackReceiver` takes, plus
`message`.

### defaultReceiver(provider)

Picks between them based on the machine and the provider. This is what `login()` uses when you pass
no receiver.

## From @ai-oauth-sdk/browser

A page cannot bind a port, so both of these route the callback back through the browser. They trade
off against each other rather than one being better; see
[popup and redirect](/docs/flows/popup-and-redirect).

### popupReceiver(options)

| Option | Type | Description |
| --- | --- | --- |
| `redirectUri` | `string` | A page on your origin that runs postCallbackToOpener() and announceCallback(). Defaults to `the current URL without its fragment`. |
| `width` | `number` |  |
| `height` | `number` |  |
| `windowName` | `string` |  |
| `pollIntervalMs` | `number` | Defaults to `400`. Not used for a provider whose authorization page severs the opener, where the handle reports a window still on screen as closed. |

### postCallbackToOpener(payload?)

Call this on your redirect page. Returns `true` when it posted to an opener and closed the window,
`false` when there was no opener to post to. Defaults to reading `window.location.search`.

### announceCallback(payload?, timeoutMs?)

The other half, for when `postCallbackToOpener()` returns `false`:

```html
<script type="module">
  import { postCallbackToOpener, announceCallback } from 'https://esm.sh/@ai-oauth-sdk/browser'
  if (!postCallbackToOpener()) {
    await announceCallback()
  }
</script>
```

Broadcasts the callback across your origin on a `BroadcastChannel`, which does not go through the
opener and so survives an authorization page that severed it (`claude.ai` does). Resolves `true`
once a waiting `popupReceiver` acknowledges, and closes this window; `false` after `timeoutMs`
(default 1500) with nothing acknowledging, which usually means nobody was waiting.

A broadcast reaches every context on your origin, so `popupReceiver` compares `state` and ignores a
callback minted for a different attempt — including one that carries no `state` at all, which is
what a stray or hostile broadcast looks like and which would otherwise cancel a live sign-in.

Nothing to compare is a different case from a disagreement. An authorization URL that carried no
`state`, or a provider declaring `echoesState: false` because its callback will not bring one back,
leaves the receiver no attempt to tell callbacks apart by, and one is taken as it comes.

### redirectReceiver(options)

Exists for completeness. Its `wait()` never settles, because the document is unloading, so use the
two helpers instead.

### startRedirectLogin(client, options) and handleRedirectCallback(client, options)

The pair that actually implements a full-page redirect. See
[popup and redirect](/docs/flows/popup-and-redirect).

## From @ai-oauth-sdk/react-native

Both take the native module as an argument rather than importing it, so the package installs in a
bare app that has none of Expo.

### deepLinkReceiver(options)

| Option | Type | Description |
| --- | --- | --- |
| `linking` | `LinkingLike` | **Required.** Linking from react-native. |
| `redirectUri` | `string` | **Required.** Your app's callback URL. |

Matches every deep link to the attempt it presented, by `state`, because a custom scheme is open to
every app on the device. One that disagrees, or that carries no `state` where one was presented, is
dropped — including `?error=...`, which RFC 6749 requires providers to echo `state` on. A provider
that does not leaves the login pending rather than failing it, so give `login()` a `timeoutMs`.

Also reads `getInitialURL()`, which is where the redirect lands when the OS killed your app while
the user was on the consent screen. That does not resume the `login()` the killed process started —
the relaunched app mints a new `state` the old URL can never match — so pass the URL to
`completeAuthorization()` yourself, from storage that survived the restart. See
[React Native](/docs/runtimes/react-native).

### authSessionReceiver(options)

| Option | Type | Description |
| --- | --- | --- |
| `webBrowser` | `WebBrowserLike` | **Required.** The expo-web-browser module. |
| `redirectUri` | `string` | **Required.** From AuthSession.makeRedirectUri(). |
| `browserOptions` | `Record<string, unknown>` | Forwarded to openAuthSessionAsync. |

## Writing one

```ts
import type { CallbackReceiver } from '@ai-oauth-sdk/core'

export function customProtocolReceiver(scheme: string): CallbackReceiver {
  return {
    id: 'custom-protocol',
    async start(context) {
      const pending = registerProtocolHandler(scheme)

      return {
        redirectUri: `${scheme}://auth/callback`,
        async present(url) {
          await context.openUrl?.(url)
        },
        async wait() {
          const incoming = await pending.next()

          return readCallback(context.provider, incoming)
        },
        async close() {
          pending.dispose()
        },
      }
    },
  }
}
```

`readCallback` from the core does the parsing and raises `authorization_denied` when the provider
sent an error instead of a code, so every receiver handles that identically.

`context` carries the resolved provider, an `openUrl` when the caller supplied one, and the login's
`AbortSignal`. Honour the signal if your receiver can wait indefinitely.
