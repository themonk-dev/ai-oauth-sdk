```ts
interface AuthStorage {
  get(key: string): Promise<string | null>
  set(key: string, value: string): Promise<void>
  delete(key: string): Promise<void>
  keys?(): Promise<string[]>
}
```

Async throughout, so it fits `AsyncStorage`, SecureStore, the filesystem and a keychain equally
well. Values are strings; the library serialises before handing anything over.

`keys()` is optional because some backends genuinely cannot enumerate. Callers degrade gracefully
when it is absent: `listStoredSessions()` returns nothing and abandoned pending records are not
pruned. Nothing else changes.

## Keys

| Key | Contents | Lifetime |
| --- | --- | --- |
| `pending:<state>` | redirect URI, PKCE verifier, expiry, metadata | until completed or `stateTtlMs` passes |
| `tokens:<provider>` | the `TokenSet` | until logout |
| `tokens:<provider>:<accountKey>` | the `TokenSet` for a named account | until logout |

Both are JSON. Nothing assumes ordering, transactions or locking.

## Built-in adapters

Each adapter package ships the storage that makes sense for its runtime, and the core ships the
three that need no platform at all. None of them is required; the interface above is the contract.

### Core

```ts
import { fromSyncStorage, memoryStorage, prefixedStorage } from '@ai-oauth-sdk/core'
```

| Helper | Type | Description |
| --- | --- | --- |
| `memoryStorage()` | `AuthStorage` | A Map. The default, and correct only within one process. |
| `prefixedStorage(inner, prefix)` | `AuthStorage` | Namespaces every key. Used for per-user isolation on a server. |
| `fromSyncStorage(storage)` | `AuthStorage` | Adapts a synchronous getItem/setItem/removeItem object. |

### Node

```ts
import { defaultAuthDir, fileStorage, listStoredSessions } from '@ai-oauth-sdk/node'
```

`fileStorage({ dir })` writes a single JSON document at mode `0600`. `defaultAuthDir()` is
`~/.ai-oauth-sdk`, or `AI_OAUTH_SDK_HOME` when set.

```ts
const sessions = await listStoredSessions()
// [{ provider: ProviderId.Claude, account: 'work', email: '...', expiresAt: ... }]
```

### Browser

```ts
import { localStorageAdapter, sessionStorageAdapter } from '@ai-oauth-sdk/browser'
```

`sessionStorage` is the default in `createBrowserAuthClient`. It survives the redirect round-trip
but not the tab, which is the safer choice for a bearer token in a page.

Both adapters fall back to memory where the browser throws on access — Safari private mode,
sandboxed iframes — and in a browser Web Worker, which has no web storage but is still one user's
browser. Where there is no browser at all, which in practice means server-side rendering,
constructing one stays harmless but reading or writing through it rejects: an in-memory store on a
server is a single `Map` shared by every request it serves. Ask for `memoryStorage()` explicitly if
that is genuinely what you want there.

<Callout type="warn" title="Cloudflare Workers is a server, whatever its global is called">
  workerd — Cloudflare Workers and Pages Functions, `@cloudflare/next-on-pages`,
  `adapter-cloudflare`, Nitro's `cloudflare_module` — exposes `WorkerGlobalScope` on its global, but
  one isolate serves request after request from different users. So "is this a Web Worker?" is
  answered by the parts of the worker API that workerd does not implement (`WorkerNavigator`, a
  `location`), and the adapters refuse there rather than handing back a `Map` that would pool every
  user's tokens. Any runtime they cannot positively identify as a browser worker is refused for the
  same reason. If you are somewhere genuinely per-user that they do not recognise, pass `storage:`
  explicitly.
</Callout>

### React Native

```ts
import { asyncStorageAdapter, secureStoreAdapter } from '@ai-oauth-sdk/react-native'
```

`secureStoreAdapter(SecureStore, options)` is backed by the iOS Keychain and Android
EncryptedSharedPreferences. It has no `keys()`, because SecureStore cannot enumerate.

## Writing one

Three methods. See [database-backed storage](/docs/recipes/storage) for Redis and SQL versions, and for
wrapping one in encryption.

```ts
export function myStorage(): AuthStorage {
  return {
    async get(key) {
      return (await backend.read(key)) ?? null
    },
    async set(key, value) {
      await backend.write(key, value)
    },
    async delete(key) {
      await backend.remove(key)
    },
  }
}
```

`get` must return `null` rather than `undefined` for a missing key. That is the contract the
registry checks against.

## Choosing one

| Situation | Adapter |
| --- | --- |
| CLI or desktop app | `fileStorage()` |
| Single-page app | `sessionStorageAdapter()` |
| Mobile app | `secureStoreAdapter()` |
| One server process | anything shared, or a file |
| Serverless, or several instances | Redis, SQL, or another shared store |
| Tests | `memoryStorage()` |

<Callout type="warn" title="memoryStorage across a request boundary will fail in production">
  Serverless functions do not share process memory, and neither do two instances behind a load
  balancer. The pending record written when the flow starts has to be readable when the callback
  arrives, and in development that is the same process, which is exactly why the bug survives
  testing.
</Callout>
