Svelte 4 and up.

The core store already satisfies Svelte's contract. `subscribe(fn)` emits the current value
immediately and returns an unsubscribe function, which is the whole of it. So this package is
mostly a re-export with Svelte's types spelled out, and `$auth` works with no adapter in between.

```svelte
<script lang="ts">
  import { createAuth } from '@ai-oauth-sdk/svelte'
  import { popupReceiver } from '@ai-oauth-sdk/browser'

  const auth = createAuth({
    provider: 'openai',
    clientId,
    receiver: popupReceiver(),
  })
</script>

{#if $auth.tokens}
  <span>{$auth.tokens.email}</span>
  <button on:click={() => auth.logout()}>Sign out</button>
{:else}
  <button disabled={$auth.isLoading} on:click={() => auth.login()}>
    {$auth.isLoading ? 'Signing in...' : 'Sign in with ChatGPT'}
  </button>
  {#if $auth.error}
    <p role="alert">{$auth.error.message}</p>
  {/if}
{/if}
```

## Sharing it

Create the store once in a module and import it wherever you need it. That is the idiomatic Svelte
answer and it avoids the two-clients problem:

```ts
// src/lib/auth.ts
import { createAuth } from '@ai-oauth-sdk/svelte'
import { popupReceiver } from '@ai-oauth-sdk/browser'

export const auth = createAuth({
  provider: 'openai',
  clientId: import.meta.env.VITE_OPENAI_CLIENT_ID,
  receiver: popupReceiver(),
})
```

## SvelteKit

A module-level store is created during SSR too, so keep anything browser-only out of the module
body. `popupReceiver()` reads `window` when it starts rather than when it is constructed, so
constructing it is safe. Storage is the thing to guard:

```ts
import { browser } from '$app/environment'
import { memoryStorage } from '@ai-oauth-sdk/core'
import { sessionStorageAdapter } from '@ai-oauth-sdk/browser'

export const auth = createAuth({
  provider: 'openai',
  clientId,
  receiver: popupReceiver(),
  storage: browser ? sessionStorageAdapter() : memoryStorage(),
})
```

A module-level store is also shared across requests on the server, which is fine when it holds
nothing (as above) and wrong the moment it holds a real session. For a server-side flow, use a
`+server.ts` endpoint and a per-user client: see
[a multi-user server](/recipes/multi-user).

## Manual lifecycle

`createAuth` returns `restore`, `cancel` and `destroy` alongside the actions. Nothing calls
`destroy` for you, because a module-level store has no component lifetime to hang it on. In a
component-scoped store, call it in `onDestroy`:

```svelte
<script>
  import { onDestroy } from 'svelte'
  const auth = createAuth({ /* ... */ })
  onDestroy(() => auth.destroy())
</script>
```
