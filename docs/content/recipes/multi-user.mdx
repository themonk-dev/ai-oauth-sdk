Give each user their own client via `accountKey`, and namespace the storage so pending flows cannot
collide.

```ts
import { createAuthClient, prefixedStorage, publicClientIds } from '@ai-oauth-sdk/core'

function clientFor(userId: string) {
  return createAuthClient({
    provider: 'openai',
    clientId: publicClientIds.openai,
    redirectUri: 'https://yourapp.com/auth/callback',
    accountKey: userId,
    storage: prefixedStorage(sharedStorage, `user:${userId}:`),
  })
}
```

`accountKey` changes the storage key the token is written under. `prefixedStorage` puts everything
that client touches, tokens and pending records alike, behind a per-user prefix. Both together mean
two users signing in at once cannot see or overwrite each other.

Building a client is cheap. There is no connection, no handshake, and no shared mutable state
beyond the storage you pass it, so constructing one per request is fine.

## The callback does not know whose it is

The provider redirects to one URL for everybody. `state` is the only thing on that request that
identifies the flow, so record its owner when you start it:

```ts
app.get('/auth/login', async (c) => {
  const userId = c.get('userId')

  const { url, state } = await clientFor(userId).createAuthorization({
    metadata: { userId },
  })

  // Remember which user owns this state, so the callback can find them again.
  await sharedStorage.set(`state-owner:${state}`, userId)

  return c.redirect(url)
})

app.get('/auth/callback', async (c) => {
  const state = new URL(c.req.url).searchParams.get('state')

  if (!state) {
    return c.text('Missing state.', 400)
  }

  const userId = await sharedStorage.get(`state-owner:${state}`)

  if (!userId) {
    return c.text('Unknown sign-in request.', 400)
  }

  const tokens = await clientFor(userId).completeAuthorization({ callbackUrl: c.req.url })

  return c.json({ signedInAs: tokens.email })
})
```

The `state-owner` entry is outside the prefixed namespace on purpose. The callback route cannot
know which prefix to look under until it has resolved the owner, which is the thing it is looking
up.

Give it a TTL that matches `stateTtlMs`, or abandoned logins accumulate.

<Callout type="warn" title="Do not use echoesState: false providers here">
  OpenRouter never returns `state`, so its flows resolve against "the most recently started one".
  In a multi-user server that means one user can complete another user's login. That mode is for
  CLIs and single-flow apps only. See [OpenRouter](/providers/openrouter).
</Callout>

## Session, not token

The token belongs to your server, not to the browser. Set your own session cookie in the callback
and keep the provider token server-side:

```ts
app.get('/auth/callback', async (c) => {
  const tokens = await clientFor(userId).completeAuthorization({ callbackUrl: c.req.url })

  // Your session, your cookie. The provider token stays in storage.
  await setSessionCookie(c, { userId, email: tokens.email })

  return c.redirect('/')
})
```

Sending the provider token to the browser turns a server-side credential into one that any script
on the page can read, and it removes your ability to revoke it.

## Making calls on behalf of a user

```ts
import { createAuthenticatedFetch } from '@ai-oauth-sdk/core'

app.post('/api/chat', async (c) => {
  const userId = c.get('userId')
  const api = createAuthenticatedFetch(clientFor(userId))

  const response = await api('/chat/completions', {
    method: 'POST',
    body: JSON.stringify(await c.req.json()),
    headers: { 'Content-Type': 'application/json' },
  })

  return new Response(response.body, { headers: response.headers })
})
```

Refresh is per client, and each request builds a fresh one, so the in-process refresh deduplication
does not apply across requests. What does apply is the cross-process check: before refreshing, the
client re-reads storage and takes the stored token if another request already rotated it. That is
what keeps two concurrent requests from invalidating each other with providers that rotate refresh
tokens.

## Encrypt the tokens

A table of OAuth tokens is a table of credentials. If your database is not already encrypted at
rest, wrap the storage adapter. That is covered in
[database-backed storage](/recipes/storage#encrypt-at-rest).
