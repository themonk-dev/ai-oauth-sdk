The flow starts on one request and finishes on another, so nothing can be held in a closure. `state`
is the only thing tying them together, which is exactly what the registry is for. See
[the state handoff](/docs/flows/state-handoff) for how that works.

The framework barely matters. All of these do the same three things.

<Tab value="Hono">

```ts
import { Hono } from 'hono'
import { createAuthClient, ProviderId, publicClientIds } from '@ai-oauth-sdk/core'

const client = createAuthClient({
  provider: ProviderId.OpenAI,
  // You name the credential. publicClientIds[ProviderId.OpenAI] is the one OpenAI's own
  // Codex CLI publishes; pass your own registered id instead if you would
  // rather not present as that CLI.
  clientId: publicClientIds[ProviderId.OpenAI],
  redirectUri: 'https://yourapp.com/auth/callback',
  storage: redisStorage(redis),
})

const app = new Hono()

app.get('/auth/login', async (c) => {
  const { url } = await client.createAuthorization()

  return c.redirect(url)
})

app.get('/auth/callback', async (c) => {
  const tokens = await client.completeAuthorization({ callbackUrl: c.req.url })

  return c.json({ signedInAs: tokens.email })
})
```

```ts
// app/auth/callback/route.ts
import { NextResponse, type NextRequest } from 'next/server'
import { isOAuthError } from '@ai-oauth-sdk/core'
import { authClient } from '@/lib/auth'

export async function GET(request: NextRequest) {
  try {
    const tokens = await authClient.completeAuthorization({ callbackUrl: request.url })

    return NextResponse.json({ signedInAs: tokens.email })
  } catch (error) {
    if (isOAuthError(error)) {
      return NextResponse.json({ error: error.code }, { status: 400 })
    }

    throw error
  }
}
```

<Callout type="warn" title="Use a shared store, not memory">
  Serverless functions do not share process memory, so the pending record written by `/auth/login`
  has to be readable by `/auth/callback`, which may be an entirely different instance.
  `memoryStorage()` will look fine in development and break in production. See
  [database-backed storage](/docs/recipes/storage).
</Callout>

## Errors worth handling

A user who clicks "Deny" comes back with `?error=access_denied`, which `completeAuthorization`
turns into an `OAuthError`. Handle it rather than letting it become a 500:

```ts
import { isOAuthError } from '@ai-oauth-sdk/core'

try {
  await client.completeAuthorization({ callbackUrl: req.url })
} catch (error) {
  if (!isOAuthError(error)) {
    throw error
  }

  switch (error.code) {
    case 'authorization_denied':
      return res.status(400).send('You declined the sign-in request.')
    case 'state_expired':
      return res.redirect('/auth/login') // took too long, just start over
    case 'unknown_state':
      return res.status(400).send('That sign-in link is no longer valid.')
    default:
      throw error
  }
}
```

`state_expired` and `unknown_state` are both ordinary. A user who left the tab open over lunch hits
the first; a user who reloaded the callback URL hits the second, because the pending record is
consumed on the way through.

## Redirecting the user somewhere sensible

The callback route has no idea what the user was doing. Carry it in the flow's metadata:

```ts
app.get('/auth/login', async (c) => {
  const { url } = await client.createAuthorization({
    metadata: { returnTo: c.req.query('returnTo') ?? '/' },
  })

  return c.redirect(url)
})

app.get('/auth/callback', async (c) => {
  const state = new URL(c.req.url).searchParams.get('state')
  const pending = state ? await client.getPendingAuthorization(state) : undefined
  const returnTo = (pending?.metadata?.returnTo as string) ?? '/'

  await client.completeAuthorization({ callbackUrl: c.req.url })

  return c.redirect(returnTo)
})
```

Read the pending record before completing, because completing consumes it. And validate `returnTo`
against your own routes rather than trusting it, or you have built an open redirect.

## One user or many

Everything above assumes a single account, which is right for a self-hosted tool or a desktop app
with a local server. The moment several people sign in through the same deployment, you need one
client per user and namespaced storage. That is [the next recipe](/docs/recipes/multi-user).
