title: Database-backed storage
description: AuthStorage is three methods and an optional fourth. Anything with a key/value shape works.

---

```ts
interface AuthStorage {
  get(key: string): Promise<string | null>
  set(key: string, value: string): Promise<void>
  delete(key: string): Promise<void>
  keys?(): Promise<string[]>
}
```

Async throughout, so it fits `AsyncStorage`, SecureStore, the filesystem and a keychain equally
well. Values are strings, because the library serialises before it hands anything over.

## Redis

```ts
import type { AuthStorage } from '@ai-oauth-sdk/core'

export function redisStorage(redis: Redis, prefix = 'aioauth:'): AuthStorage {
  return {
    async get(key) {
      return redis.get(prefix + key)
    },
    async set(key, value) {
      // Pending records expire on their own, but a TTL keeps abandoned flows
      // from lingering in Redis regardless.
      await redis.set(prefix + key, value, key.startsWith('pending') ? { EX: 900 } : {})
    },
    async delete(key) {
      await redis.del(prefix + key)
    },
    async keys() {
      // Optional. Enables listStoredSessions() and the pruning of abandoned
      // flows. Omit it and both simply do nothing.
      const found = await redis.keys(`${prefix}*`)

      return found.map((key) => key.slice(prefix.length))
    },
  }
}
```

## SQL

The same shape over one table of `(key TEXT PRIMARY KEY, value TEXT)`:

```ts
export function sqlStorage(db: Database): AuthStorage {
  return {
    async get(key) {
      const row = await db.get('SELECT value FROM auth_store WHERE key = ?', key)

      return row?.value ?? null
    },
    async set(key, value) {
      await db.run(
        'INSERT INTO auth_store (key, value) VALUES (?, ?) ' +
          'ON CONFLICT (key) DO UPDATE SET value = excluded.value',
        key,
        value,
      )
    },
    async delete(key) {
      await db.run('DELETE FROM auth_store WHERE key = ?', key)
    },
    async keys() {
      const rows = await db.all('SELECT key FROM auth_store')

      return rows.map((row) => row.key)
    },
  }
}
```

## On the optional keys()

Two things use it, and both degrade to nothing when it is missing:

- `listStoredSessions()` in the Node adapter, which is what `ai-oauth-sdk list` prints.
- Pruning expired pending records, so abandoned flows do not accumulate.

It is optional because some backends genuinely cannot enumerate. Expo's SecureStore is the
motivating case. Give the store a TTL instead, as the Redis adapter above does, and nothing is
lost.

## Encrypt at rest

Tokens are bearer credentials. Anyone holding one is the user. If the database is not already
encrypted, wrap the adapter:

```ts
export function encrypted(inner: AuthStorage, key: CryptoKey): AuthStorage {
  return {
    get: async (k) => {
      const stored = await inner.get(k)

      return stored ? decrypt(stored, key) : null
    },
    set: (k, v) => inner.set(k, encrypt(v, key)),
    delete: (k) => inner.delete(k),
    ...(inner.keys ? { keys: () => inner.keys() } : {}),
  }
}
```

Note the spread on the last line. Copying `keys` unconditionally would attach an `undefined`
property, and the library checks for presence rather than for callability.

## Built-in helpers

```ts
import { fromSyncStorage, memoryStorage, prefixedStorage } from '@ai-oauth-sdk/core'
```

| Helper | Type | Description |
| --- | --- | --- |
| `memoryStorage()` | `AuthStorage` | A Map. The default, and correct only within one process. |
| `prefixedStorage(inner, prefix)` | `AuthStorage` | Namespaces every key. Used for per-user isolation. |
| `fromSyncStorage(storage)` | `AuthStorage` | Adapts a synchronous get/set/removeItem object, such as a Web Storage area. |

## What gets stored

Two kinds of key.

- `pending:<state>` holds a started flow: the redirect URI, the PKCE verifier, the expiry, and any
  metadata. Short-lived, consumed on completion.
- `tokens:<provider>` or `tokens:<provider>:<accountKey>` holds the `TokenSet`.

Both are JSON. Nothing in the library assumes an ordering, a transaction, or a lock, so an
eventually consistent store is fine as long as a write is visible to the process that reads it next.
