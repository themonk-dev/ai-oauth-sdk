The process prints an authorization URL. The user opens it wherever their browser actually is,
approves, and pastes what they get back. No port is bound and no redirect has to reach the machine.

That makes it the right answer for SSH sessions, containers, CI, and any provider that only
supports a hosted callback page.

```ts
import { promptReceiver } from '@ai-oauth-sdk/node'

const tokens = await client.login({ receiver: promptReceiver() })
```

```bash
ai-oauth-sdk login claude --paste
```

## What the user pastes

Whatever the provider gave them. The receiver hands the raw string to the provider's own parser, so
all three of these work:

```
http://localhost:1455/auth/callback?code=abc123&state=xyz789
abc123#xyz789
abc123
```

Claude's hosted page hands back `code#state` as one opaque string rather than a URL, which is
why the parsing is per-provider rather than a single regex.

A bare code with no `state` is accepted only from providers that documented they do not echo it.
Everywhere else the login is rejected, because a callback that cannot be matched to the flow that
started it is indistinguishable from a forged one.

## Options

| Option | Type | Description |
| --- | --- | --- |
| `redirectUri` | `string` | Where the provider should send the user. Defaults to `the provider's hosted callback page`. |
| `openBrowser` | `boolean` | Also try to open a browser locally, in case there is one. Defaults to `true`. |
| `message` | `(url: string) => string` | Replaces the printed instructions. |
| `signal` | `AbortSignal` | Abandons the pending read. Used when racing this against another receiver. |
| `retryOnInvalidPaste` | `boolean` | Report the problem and ask again instead of failing the login. Defaults to `false`. |

`retryOnInvalidPaste` is off by default because the prompt is usually the only way the login can
finish, and a user holding a value that will never parse would have nothing left but Ctrl-C. Turn it
on where something else can end the wait — a receiver racing this one, or `signal`. `hybridReceiver`
turns it on for you, and only when its loopback half actually bound. A pasted *denial* is never
retried either way: the provider answered, and the answer was no.

## Do not make users choose

A user who reaches for `--paste` on their own laptop, where a loopback server would have worked
fine, used to get the worst of both: the redirect landed on a port nothing was listening on, the
browser showed "This site can't be reached", and the code was only recoverable out of the address
bar.

Since the port is known up front, the fix is to listen on it anyway. `hybridReceiver` starts both
halves and takes whichever finishes first:

```ts
import { hybridReceiver } from '@ai-oauth-sdk/node'

await client.login({ receiver: hybridReceiver() })
```

Three details keep that race honest:

- **The listener is best-effort about the machine, never about the address.** A sandbox that
  forbids `listen()` is exactly the condition pasting exists to serve — the redirect URI stays
  unclaimed because nothing here can claim it — so that failure degrades to the prompt alone rather
  than ending the login before the URL is even shown. A port already *held* is the opposite
  situation: someone else is listening on the exact URI both halves are about to advertise, so
  carrying on would print an authorization URL naming an address this process does not own and let
  the browser deliver the code to whoever does. `loopbackReceiver` refuses to start under that
  arrangement, and `hybridReceiver` propagates the refusal instead of pasting past it — so
  `start()` rejects, and `ai-oauth-sdk login <provider> --paste` reports the contested port rather
  than prompting. The two are told apart by type: a refusal is an `OAuthError`, and a kernel saying
  no is not.
- **A slip at the prompt does not compete. An answer does, either way.** A blank line or a mistyped
  paste is not an answer, and letting it win would tear down a server that was about to receive a
  perfectly good callback. It is not discarded either: the prompt says what was wrong and asks
  again, on the same open readline, for as long as the server is still listening. What still travels
  is the provider's own refusal — the `?error=access_denied` a user copies back after clicking Deny.
  No callback is coming after that, so the login ends with it, exactly as the same denial does when
  it arrives on the port instead.
- **Only the prompt announces the URL.** `present()` is what opens the browser, and two halves
  announcing means two tabs on the same authorization URL.

Both halves have to advertise the same redirect URI, since the provider matches it against the
value replayed at the code exchange, and an ephemeral port is only known once the server has bound.

## Building your own prompt

`promptReceiver` is a thin wrapper over `manualReceiver` from the core, which takes any async
function returning a string. That is the hook for a TUI, a GUI dialog, or a test:

```ts
import { manualReceiver } from '@ai-oauth-sdk/core'

const receiver = manualReceiver({
  redirectUri: 'https://example.com/callback',
  async prompt(url) {
    return await showModalAndAwaitPaste(url)
  },
})
```

`prompt` is called once per attempt. To ask again after a value that could not be read as a code,
add `retry` — it is handed the error that would otherwise have ended the login, and returning `true`
runs `prompt` again:

```ts
const receiver = manualReceiver({
  async prompt(url) {
    return await showModalAndAwaitPaste(url)
  },
  retry(error, attempts) {
    if (error.code !== 'invalid_token_response' || attempts >= 3) {
      return false
    }

    showMessage(error.message)

    return true
  },
})
```

A `prompt` that *rejects* is never retried: that is the read being abandoned — an abort, a closed
stdin — rather than an answer to reject, and reopening it is how a race this half already lost would
fail to finish.
