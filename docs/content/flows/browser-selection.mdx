Every other page in this section describes a mechanism: loopback, popup, device code, paste. None of
them says which one a given provider will hand you on a given origin. Today that gets discovered by
trying, and the two facts below each cost a live probe to pin down.

## The question, in order

Ask these three, in this order, and stop at the first yes.

**1. Can this origin produce a redirect URI the provider's registered client accepts?** If so, the
answer is [popup](/docs/flows/popup-and-redirect), with that URI.

- The origin is loopback and the provider's redirect spec is `loopbackPort: 0` — "any free port" —
  or it names a fixed port and host that the origin happens to match.
- The origin is HTTPS (or anything non-loopback) and the provider's registered client accepts an
  arbitrary HTTPS redirect rather than confining itself to loopback.

**2. Does the provider support a device flow?** If so, the answer is
[device code](/docs/flows/device-code), regardless of what the origin is. A device flow needs
nothing redirected anywhere, so the origin question never even applies. Check both
`deviceAuthorizationUrl` and `deviceFlow` — OpenAI has only the latter, because its device flow
predates and does not follow RFC 8628.

**3. Otherwise, [paste](/docs/flows/manual-paste).** What the reader copies depends on what the
redirect would have done: a provider with a hosted callback page (`redirect.hostedUri`) shows a code
on its own page, and that is what gets copied. A provider with only a loopback redirect sends the
browser to a `localhost` URL that fails to load, and the code exists nowhere but that dead address
bar — which is why the tab must not be closed before it is copied out.

## The matrix

For the seven built-in providers, on a page served from a loopback origin
(`http://localhost:PORT`) versus one served over HTTPS:

| Provider | Loopback redirect | HTTPS redirect | Device flow | Loopback origin | HTTPS origin |
| --- | --- | --- | --- | --- | --- |
| `openrouter` | any port | accepted (no fixed client to reject it) | no | popup | popup |
| `claude` | any port | accepted — verified live | no | popup | popup |
| `gemini` | any port | rejected — verified live | no | popup | paste |
| `openai` | port `1455` fixed | untested, moot | yes, not RFC 8628 | device | device |
| `xai` | port `56121`, host `127.0.0.1` | untested, moot | yes | device | device |
| `github-copilot` | none registered | not applicable | yes | device | device |
| `qwen` | none registered | not applicable | yes | device | device |

"Untested, moot" means the provider supports a device flow, so question 2 answers it before question
1's HTTPS case is ever reached — whether the client would also accept an arbitrary HTTPS redirect was
never worth finding out. `github-copilot` and `qwen` have no redirect-based flow registered at all;
question 1 has nothing to evaluate for either origin.

Two of those cells are not read off a descriptor. **Claude's** registered client accepts an
arbitrary HTTPS redirect: `https://claude.ai/oauth/authorize` opened in a signed-in browser, with the
published Claude Code client id and `redirect_uri=https://chat.themonk.dev/callback`, rendered the
consent screen rather than a `redirect_uri_mismatch`. **Gemini's** does not: the same experiment,
same browser, same signed-in account, minutes apart, with the published gemini-cli client id, came
back `Error 400: redirect_uri_mismatch`. Consistent with Google confining installed-app clients to
loopback. One browser, one account, opposite answers — that contrast is what makes both conclusive.

## Why the origin changes the answer at all

RFC 8252 says an authorization server should ignore the port when matching a registered loopback
redirect URI, precisely so a native app can bind an ephemeral one. A page served from
`http://localhost:PORT` *is* such a URI for a client registered with `loopbackPort: 0` — the popup's
redirect target is a page the app itself already controls, on the app's own origin, and
`postMessage` back to the opener works the same way it does for a desktop CLI's loopback server.

Deploy that same app to `https://your-app.example`, and the loopback match is gone. Whether the
popup still works now depends entirely on whether the provider's registered client also accepts an
arbitrary HTTPS redirect — a second, independent grant that has nothing to do with loopback and that
most providers never had a reason to document, because their own CLI never asks for it.

## A property of the client, not of OAuth

Nothing above is a limitation of the protocol or of this library. It is a fact about what each
provider's specific registered client was configured to accept when it was created. A CLI client
registered for loopback redirects rejects an HTTPS one no matter which library sends the request —
the descriptor's `mode: 'loopback'` plus an optional `hostedUri` fallback is what this SDK ships for
each provider, and for Claude that shape actually understates what the client permits, since the
extra HTTPS grant is real but was never documented anywhere this library could read it from.

That is also why the matrix above cannot be extended to a provider that is not listed here just by
reasoning about OAuth in general. A custom provider's browser behavior depends on how its own client
was registered, and finding out means asking it the same way the two facts above were found: by
trying a redirect and reading what comes back.
